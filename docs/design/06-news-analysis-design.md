## 1. 목적

임베딩·클러스터링 단계에서 이슈로 묶인 뉴스 클러스터를 받아 **분류 → 콘텐츠 생성 → Issue Docent 발행**까지 수행한다.

파이프라인에서의 위치:

```
수집 → 전처리 → 임베딩·클러스터링 → [뉴스 분석] → Issue Docent 생성
```

뉴스 분석의 산출물:

| 산출물 | 설명 |
|-------|------|
| 분류 결과 | L1·L2·L3 태그 부여 |
| 콘텐츠 본문 | 4 head 고정 구조의 주린이용 설명 |
| 연결 모듈 데이터 | 관련 섹터·기업 부채살 |
| Issue Docent | 클러스터 단위 발행 콘텐츠 |
| 퀴즈 데이터 | 독해·체크포인트 퀴즈 |

## 2. 기획 의도

주식 뉴스 하나는 여러 성격을 동시에 갖는다. 예를 들어 `정부, AI 반도체 세액공제 확대 검토에 반도체주 강세`라는 뉴스는 정책 뉴스이자 반도체 산업 뉴스이고, AI 테마 뉴스이자 주가 뉴스이기도 하다. 단일 분류로는 이 뉴스의 성격을 충분히 설명할 수 없다.

분류의 용도도 서로 다르다.

- 사용자 화면에 보여줄 카테고리 → 직관적이어야 함
- LLM이 사용할 라벨 → 요약 방향을 결정해야 함
- 추천·학습에 쓰는 태그 → 검색과 학습에 연결되어야 함

이 세 가지 용도를 하나의 분류로 처리하면 모두 어정쩡해진다. 분류를 **세 개의 레이어**로 분리해 각각의 목적에 맞게 운영한다.

---

## 3. 분류 구조 개요

| 레이어 | 이름 | 개수 | 사용자 노출 | 역할 |
|--------|------|------|-----------|------|
| **L1** | 뉴스 유형 | 5개 | ✅ 노출 | 이 뉴스가 무엇에 대한 뉴스인가 |
| **L2** | 해석 프레임 | 6개 | ❌ 내부 | 어떤 관점으로 읽어야 하는가 — 본문 구조·번역·퀴즈의 기준 |
| **L3** | 태그 | 복수 | 일부 노출 | 추천, 검색, 학습에 사용하는 메타데이터 |

---

## 4. L1 뉴스 유형

L1은 5개로 한다. 6개 이상이 되면 잘 사용되지 않는 카테고리가 생겨 인지 부하가 높아진다.

| 분류 | 정의 | 예시 |
|------|------|------|
| **기업** | 특정 기업 한 곳이 주체인 뉴스 | 삼성전자 3분기 영업이익 9.2조 |
| **산업·테마** | 산업 또는 트렌드 전체에 영향을 주는 뉴스 | AI 데이터센터 수요로 HBM 공급 부족 |
| **시장·수급** | 지수, 거래대금, 외국인·기관 매매, ETF 자금 흐름 | 코스피 외국인 8거래일 연속 순매수 |
| **정책·규제** | 정부, 중앙은행, 규제기관의 결정 및 발표 | 한은 기준금리 0.25%p 인하 |
| **글로벌·이슈** | 해외 거시·지정학 이슈 중 국내 시장에 영향을 주는 것 | 미 연준 점도표 매파적, 나스닥 급락 |

**통합 결정 근거:**

- 산업 뉴스와 테마 뉴스는 실제 기사에서 거의 항상 함께 등장 → L1에서 통합, 구분은 L3 태그에서 처리
- 거시경제 뉴스 → 정책·규제에 흡수
- 금융상품 자금 흐름 → 시장·수급에 흡수

---

## 5. L2 해석 프레임

L2는 6개로 한다. 같은 L1 뉴스라도 어떤 관점으로 읽어야 하는지에 따라 본문 구조와 번역 톤이 달라진다.

| 분류 | 정의 |
|------|------|
| **실적·재무** | 분기·연간 실적, 가이던스, 컨센서스 비교 |
| **제품·기술·계약** | 신제품, 신기술, 수주, 협업 |
| **산업·경쟁 구조** | 산업의 수요·공급·가격·점유율 변화 |
| **정책·규제 영향** | 정책, 세제, 규제 변화의 영향 |
| **리스크·이슈** | 사고, 소송, 회계, 경영진 이슈, 악재성 공시 |
| **주가·수급** | 주가 급등락, 수급 변화, 시장 반응 |

**통합 결정 근거:**

- 수주·계약·고객 확보 → 단독 분류로 빈도가 낮아 제품·기술·계약에 통합
- 자본정책·공시 이벤트 → 초기 범위에서는 리스크·이슈에 흡수, 추후 별도 분류 분리
- 자금 흐름·투자 상품 → L1 시장·수급과 같은 결이므로 L2에서는 다루지 않음

---

## 6. L1 × L2 매트릭스

30개 조합 중 핵심 조합은 9개이며, 초기 범위에서는 이 9개에 대해 별도 본문 템플릿을 둔다.

| | 실적·재무 | 제품·기술·계약 | 산업·경쟁 구조 | 정책·규제 영향 | 리스크·이슈 | 주가·수급 |
|--|---------|-------------|-------------|-------------|----------|---------|
| **기업** | 핵심 | 핵심 | 약함 | 가능 | 핵심 | 충돌 |
| **산업·테마** | 드뭄 | 가능 | 핵심 | 핵심 | 드뭄 | 가능 |
| **시장·수급** | × | × | × | 충돌 | 가능 | 핵심 |
| **정책·규제** | × | × | 충돌 | 핵심 | 가능 | 충돌 |
| **글로벌·이슈** | 가능 | 드뭄 | 가능 | 핵심 | 핵심 | 가능 |

**핵심 조합 9개:**

1. 기업 × 실적·재무
2. 기업 × 제품·기술·계약
3. 기업 × 리스크·이슈
4. 산업·테마 × 산업·경쟁 구조
5. 산업·테마 × 정책·규제 영향
6. 시장·수급 × 주가·수급
7. 정책·규제 × 정책·규제 영향
8. 글로벌·이슈 × 정책·규제 영향
9. 글로벌·이슈 × 리스크·이슈

핵심 조합이 아닌 나머지 조합은 가장 가까운 핵심 조합의 head 세트를 재사용한다.

## 7. 충돌 조합 처리 룰

같은 기사가 두 L1에 걸쳐 보일 때 처리 기준:

| 충돌 케이스 | 처리 룰 |
|-----------|--------|
| 기업 vs 주가·수급 | 주가 움직임이 본문의 다수를 차지하면 시장·수급. 기업 펀더멘털이 본문 핵심이면 기업 |
| 정책·규제 vs 주가·수급 | 정책 자체가 본문 핵심이면 정책·규제. 시장 반응이 본문 핵심이면 시장·수급 |
| 정책·규제 vs 산업·경쟁 구조 | 정책 발표 시점에서 1주일 이내는 정책·규제. 이후 영향 분석 기사는 산업·테마 |

**LLM 분류 우선순위:**

```
1. 기사의 상당 부분이 한 기업의 사건을 다루면 → 기업
2. 정부·규제기관·중앙은행의 결정과 발표가 본문 시작점이면 → 정책·규제
3. 해외에서 발생한 사건이 본문 시작점이면 → 글로벌·이슈
4. 지수, 거래대금, 수급 변화가 본문 시작점이면 → 시장·수급
5. 산업이나 트렌드 전체의 변화가 본문 시작점이면 → 산업·테마
```

**분류 일반 원칙**: 원인 사건을 L1으로, 결과와 해석을 L2로 분류한다.

## 8. L3 태그

L3 태그는 추천, 검색, 학습에 사용된다.

| 태그 | 구조 | 역할 |
|------|------|------|
| `sector_tags` | 폐쇄형 (반도체, 2차전지, 바이오, 금융, 조선, 방산, 플랫폼 등) | 산업 단위 필터링, 섹터 퀴즈 연결 |
| `company_tags` | `{ticker, name, role: primary\|mentioned}` | 관심 종목 알림, 종목 페이지 뉴스 묶음 |
| `theme_tags` | 개방형, 시간에 따라 확장 (AI, 데이터센터, 비만치료제, 전력망 등) | 트렌드 묶음 |
| `term_tags` | 폐쇄형 용어 사전 연동 (컨센서스, 가이던스, 선반영, ETF 등) | 본문 내 클릭형 용어 풀이, 용어 퀴즈 |
| `difficulty` | `초급 \| 중급 \| 고급` | 초보 모드 필터링 (초기에는 내부 전용) |

**`company_tags` 구분 규칙:**

직접 관련 기업(`primary`)과 단순 언급 기업(`mentioned`)을 반드시 구분한다.

```
예시: "삼성전자 호실적에 SK하이닉스도 강세"
  primary:   삼성전자
  mentioned: SK하이닉스
```

이 구분이 빠지면 추천 품질과 연결 모듈 정확도가 흔들린다.

**운영 방침:**

- `theme_tags`: 초기 범위에서는 좁게 시작하고 시장 흐름에 따라 점진적으로 확장
- `difficulty`: 초기 범위에서는 LLM이 내부적으로만 부여, 사용자 노출은 추후 적용

## 9. 분류 적용 기준

| 레이어 | 부여 수 | 조건 |
|--------|--------|------|
| L1 | 1개 (필수) | 항상 1개 |
| L2 | 1개 (필수) | 신뢰도 낮으면 `불확실` 상태 허용 |
| sector_tags | 복수 | 필수 |
| company_tags | 복수 | 필수 |
| term_tags | 복수 | 필수 |
| theme_tags | 복수 | 해당하는 경우에만 |

분류는 LLM이 자동으로 수행하고, 신뢰도가 낮은 케이스는 **별도 검수 큐**로 분리한다.

| 사용자 노출 항목 | 내부 라벨 항목 |
|--------------|-------------|
| L1, sector_tags, company_tags | L2, term_tags, difficulty |

## 10. 콘텐츠 구조 — 본문과 연결 모듈

한 이슈의 콘텐츠는 **이슈 본체**와 **연결 모듈** 두 부분으로 나뉜다.

```
[이슈 본체]  — 이슈만 단독으로 설명 (head 4칸 고정)
   1. 무슨 일이에요
   2. 왜 중요한가요         ← L2가 결정
   3. ★오해 방지            ← L2가 결정
   4. 앞으로 뭘 보면 될까요  ← L2 후속 체크포인트
─────────────────────────────
[연결 모듈]  — 별도 블록, 여기서 처음 기업이 등장
   관련 섹터 → 관련 종목 → 기업 상세 페이지
```

**설계 의도:**

- 1번(열기)과 4번(체크포인트)은 모든 뉴스가 공유
- 가운데 2번·3번만 L2에 따라 달라짐
- head 세트를 고르는 기준은 **L2**, L1은 열기 head의 말투와 연결 모듈의 모양만 바꿈

**연결 모듈 분리 이유:**

관련 섹터·기업을 본문에 넣지 않고 맨 끝 연결 모듈로 분리한다. 사용자가 오해 방지와 체크포인트를 모두 읽은 다음에야 종목으로 넘어가게 되어, "이 뉴스 = 이 종목을 사라"는 오해를 구조적으로 막는다. 투자 추천이 아니라 읽는 관점을 학습시킨다는 서비스 정체성과 일치한다.

## 11. 콘텐츠 생성의 두 관점

분류는 두 개의 다른 산출물을 만든다.

| 관점 | 정의 | 노출 여부 |
|------|------|---------|
| **프롬프트 질문** | LLM이 콘텐츠를 만들기 위해 답해야 하는 질문 | 사용자에게 노출하지 않음 |
| **노출 head** | 사용자가 화면에서 읽는 중간 제목 | 노출함 |

노출 head는 프롬프트 질문의 겉면이다. 같은 뼈대인데 하나는 의문문(내부 생성용), 하나는 읽는 렌즈(외부 노출용)다.

| 프롬프트 질문 (내부) | 노출 head (외부) |
|------------------|----------------|
| 컨센서스 대비 어떤가 | 시장 예상과 비교하면 |
| 누구에게 영향이 가나 | 누구한테 이득·부담일까요 |
| 확정인가 검토인가 | 확정된 건가요, 검토 중인가요 |

같은 L1×L2면 같은 프롬프트 질문 세트 → 같은 head 세트가 나온다. 사용자는 같은 유형의 뉴스를 매번 같은 head 순서로 읽으면서 "이 유형은 이렇게 읽는다"를 반복 학습한다.

## 12. L2별 상세 — 프롬프트 질문·노출 head·후속 체크포인트

각 L2는 프롬프트 질문 3개 + 노출 head 4개 + 후속 체크포인트를 갖는다.

프롬프트 질문은 다음 5가지 목적을 충족하도록 설계한다:

1. 기사 사실 확인
2. 왜 중요한지 이해
3. 기대감과 실제 변화 구분
4. 오해 방지
5. 다음 기사 체크포인트 도출

> head 표기에서 ★는 그 유형의 **오해 방지 head**다. 주린이가 가장 자주 하는 오해를 구조적으로 막는 칸이다.

---

### 실적·재무

**프롬프트 질문**
1. 가장 크게 좋아지거나 나빠진 숫자는 무엇이고, 그 변화를 만든 부문은 어디인가
2. 컨센서스를 상회·하회했는가, 폭은 얼마인가
3. 이 변화는 일회성 요인인가, 구조적으로 이어질 수 있는가

**노출 head**
1. 무슨 일이에요 (실적 핵심 숫자)
2. 시장 예상과 비교하면
3. ★이게 계속될까요
4. 앞으로 뭘 보면 될까요

**후속 체크포인트**: 다음 분기 가이던스, 동종업체 실적 비교

---

### 제품·기술·계약

**프롬프트 질문**
1. 새 제품·기술·계약이 기존 대비 무엇이 구체적으로 달라졌는가
2. 이 변화가 실제 매출·수익으로 연결되는 경로는 무엇인가
3. 매출 인식까지 남은 관문(인증·양산·공급계약·규제)은 무엇인가

**노출 head**
1. 무슨 일이에요 (신제품·계약 내용)
2. 기존과 뭐가 다른가요
3. ★진짜 돈이 되려면
4. 앞으로 뭘 보면 될까요

**후속 체크포인트**: 양산 일정, 첫 매출 인식 시점, 후속 수주

---

### 산업·경쟁 구조

**프롬프트 질문**
1. 수요·공급·가격·점유율 중 무엇이 어떤 방향으로 변하고 있는가
2. 유리해지는 쪽과 불리해지는 쪽은 어떤 성격의 기업인가 (기업명이 아니라 유형)
3. 단기 사이클인가, 구조적 변화인가

**노출 head**
1. 무슨 일이에요 (산업 변화)
2. 왜 중요한가요
3. ★잠깐인가요, 계속될 변화인가요
4. 앞으로 뭘 보면 될까요

**후속 체크포인트**: 가격 추이, 재고 수준, 경쟁사 캐파 발표

---

### 정책·규제 영향

**프롬프트 질문**
1. 무엇이 어떻게 바뀌며, 확정인가 검토 단계인가, 시행 시점은 언제인가
2. 이득을 보는 쪽과 부담을 지는 쪽은 어떤 성격의 산업·기업인가
3. 시장이 이미 선반영한 부분과 아직 확인 안 된 부분은 무엇인가

**노출 head**
1. 무슨 정책이에요
2. 누구한테 이득·부담일까요
3. ★확정된 건가요, 검토 중인가요
4. 앞으로 뭘 보면 될까요

**후속 체크포인트**: 시행 시점, 세부 시행령, 업계 대응

---

### 리스크·이슈

**프롬프트 질문**
1. 정확히 무슨 일이 일어났고, 확정된 사실과 미확정 사실은 무엇인가
2. 사업·재무에 미치는 영향의 범위와 크기는 어느 정도인가
3. 회복 가능한 일회성인가, 구조적으로 이어질 문제인가

**노출 head**
1. 무슨 일이에요 (사건)
2. 얼마나 영향을 줄까요
3. ★일시적인가요, 계속될 문제인가요
4. 앞으로 뭘 보면 될까요

**후속 체크포인트**: 회사 공식 입장, 후속 공시, 동종업체 영향

---

### 주가·수급

**프롬프트 질문**
1. 무엇이 얼마나 움직였고, 같은 섹터가 함께 움직였는가
2. 기사가 제시한 원인은 무엇인가
3. 그 원인은 펀더멘털로 확인된 것인가, 사후 해석인가

**노출 head**
1. 무슨 일이에요 (무엇이 얼마나 움직임)
2. 왜 이렇게 움직였대요
3. ★진짜 이유일까요, 끼워 맞춘 걸까요
4. 앞으로 뭘 보면 될까요

**후속 체크포인트**: 다음 거래일 흐름, 펀더멘털 뉴스 동반 여부

---

## 13. 9개 조합 → head 세트 매핑

head 세트는 L2가 결정하므로, 9개 핵심 조합이 실제로는 6개 세트로 모인다. L1은 열기 head의 말투와 연결 모듈 모양만 바꾼다.

| 조합 | head 세트 (L2) | L1이 바꾸는 것 |
|------|-------------|-------------|
| 기업 × 실적·재무 | 실적·재무 | — |
| 기업 × 제품·기술·계약 | 제품·기술·계약 | — |
| 기업 × 리스크·이슈 | 리스크·이슈 | 열기 head "무슨 일이에요" |
| 산업·테마 × 산업·경쟁 구조 | 산업·경쟁 구조 | 연결 모듈 = 섹터 부채살 |
| 산업·테마 × 정책·규제 영향 | 정책·규제 영향 | 연결 모듈 = 섹터 부채살 |
| 시장·수급 × 주가·수급 | 주가·수급 | 연결 모듈 = 주도 섹터·종목 |
| 정책·규제 × 정책·규제 영향 | 정책·규제 영향 | 열기 head "무슨 정책이에요" |
| 글로벌·이슈 × 정책·규제 영향 | 정책·규제 영향 | 열기 head "해외에서 무슨 일이에요", head 2 "우리 시장엔 어떻게 올까요" |
| 글로벌·이슈 × 리스크·이슈 | 리스크·이슈 | 열기 head "해외에서 무슨 일이에요", head 2 "우리 시장엔 어떻게 올까요" |

핵심 조합이 아닌 나머지 조합은 별도 head 세트를 만들지 않는다. L2가 같은 핵심 조합의 head를 그대로 쓰고, 열기 head만 L1에 맞춰 바꾼다.

## 14. 연결 모듈

본문과 시각적으로 분리된 독립 모듈이다. 여기서 처음으로 구체적인 섹터·기업이 등장하고, 각 기업 카드는 기업 상세 페이지로 이어진다.

**L1별 부채살 형태:**

| L1 | 연결 모듈 구조 |
|----|------------|
| 기업 | 주체 기업(상세 페이지) + 같은 섹터 연관·경쟁 기업 2~3 |
| 산업·테마 | 영향받는 하위 섹터별 → 섹터당 대표 기업 2~3 |
| 정책·규제 / 글로벌 | 수혜 섹터와 부담 섹터로 분리 → 섹터당 기업 |
| 시장·수급 | 그날 주도한 섹터·종목 |

**데이터 소스**: L3의 `sector_tags`와 `company_tags(primary/mentioned)`에서 끌어온다.

**카피 원칙**: 추천이 아니라 길 안내. "주목할 종목"이 아니라 "이 이슈와 관련된 종목"으로 표기한다.

## 15. 주린이 번역 작성 규칙

주린이 번역은 본문 각 head 안에 들어가는 본문 글이다. head 구조가 뼈대라면, 이 규칙은 그 안을 채우는 문장의 톤과 표현을 정한다.

**투자 권유로 오인될 수 있는 표현 금지:**

```
❌ 사용 금지: 유망하다, 사야 한다, 기회다, 수혜주, 확실하다, 급등 예상
✅ 사용 권장: 가능성이 언급되고 있다, 관심을 받고 있다, 영향을 받을 수 있다,
              보도에 따르면, 단기적으로 주가가 움직였다
```

**톤 원칙:**

1. 단어는 쉽게, 사고는 어른답게 — "어쩌면", "혹시" 같은 유아어 금지
2. 확신 대신 구분 — "좋다/나쁘다"가 아니라 "이런 측면과 저런 면이 같이 있다"
3. 설명과 판단 분리 — 사실은 단정적으로, 해석은 조심스럽게

**용어 처리**: `term_tags`에 등록된 용어는 번역 문장에 다 녹이지 않고, 본문 내 **클릭형 용어 풀이**로 분리한다.

## 16. 퀴즈 연계 방식

퀴즈는 4종으로 구성한다.

| 퀴즈 유형 | 기사 연동 | 데이터 소스 |
|---------|---------|-----------|
| 독해 퀴즈 | ✅ 연동 | 기사 본문 사실 확인 |
| 후속 체크포인트 퀴즈 | ✅ 연동 | L2 후속 체크포인트 |
| 용어 퀴즈 | ❌ 비연동 | `term_tag` 사전 |
| 섹터 상식 퀴즈 | ❌ 비연동 | `sector_tag` 사전 |

**후속 체크포인트 퀴즈 예시:**

```
[기사] AI 수요 기대에 반도체 강세

[퀴즈] 이 기사 이후 다음 반도체 뉴스에서 가장 먼저 확인할 것은?

  ① 주가 흐름
  ② 실제 수주와 매출 가이던스 변화   ← 정답
  ③ 경쟁사 주가
  ④ CEO 인터뷰

[해설] 기대가 실제 수주와 매출로 연결되는지 확인하는 것이 핵심.
       ①③은 결과, ④는 발언이라 근거가 약하다.
```

오답 선택지는 그럴듯해 보이지만 핵심을 빗나간 항목으로 구성한다.

## 18. NewsAnalysisAgent 설계

`NewsAnalysisAgent`는 `EmbeddingClusterer` 완료 후 트리거되는 LangGraph 기반 에이전트로, [2계층 오케스트레이션 모델](./00-workflow-airflow.md#2계층-오케스트레이션-모델)의 **L2 — AI 에이전트 오케스트레이션**에 해당한다. 파이프라인에서 LLM이 흐름을 판단하는 **유일한 단계**다(나머지 수집~임베딩은 L1 정형 Airflow Task → [00](./00-workflow-airflow.md), [01](./01-pipeline-orchestration-design.md)).

도입은 **단계적**으로 한다 — 18.1·18.2는 **MVP 단일 에이전트** 설계, [18.3](#183-멀티-에이전트-오케스트레이션-슈퍼바이저-워커--승급-설계)은 품질이 단일 에이전트로 부족할 때의 **멀티 에이전트(슈퍼바이저-워커)** 승급 설계다.

### 18.1 에이전트 도구 (Tools)

| 도구 | 역할 |
|------|------|
| `fetch_clusters_tool()` | 분석 대상 클러스터 조회 (`is_analyzed=False`) |
| `classify_tool(news)` | L1·L2·L3 분류 (LLM 호출) |
| `generate_content_tool(news, l2_frame)` | 4 head 본문 생성 (LLM 호출) |
| `generate_quiz_tool(analysis)` | 퀴즈 생성 |
| `build_connection_module_tool(tags)` | 연결 모듈 데이터 조립 |
| `publish_docent_tool(cluster_id)` | IssueDocent 발행 |
| `enqueue_review_tool(news_id)` | 신뢰도 낮은 케이스 검수 큐 등록 |

### 18.2 에이전트 플로우 (LangGraph)

```python
class NewsAnalysisState(TypedDict):
    clusters: list[dict]
    current_cluster_id: str
    classified_news: list[dict]
    low_confidence_ids: list[int]  # 검수 큐 대상
    generated_content: list[dict]
    docent_ready: bool
    errors: list[str]

workflow = StateGraph(NewsAnalysisState)
workflow.add_node("fetch",            fetch_node)
workflow.add_node("classify",         classify_node)      # L1·L2·L3
workflow.add_node("generate_content", generate_content_node)
workflow.add_node("build_connection", build_connection_node)
workflow.add_node("generate_quiz",    generate_quiz_node)
workflow.add_node("publish",          publish_node)
workflow.add_node("enqueue_review",   enqueue_review_node)

workflow.set_entry_point("fetch")
workflow.add_edge("fetch",            "classify")
workflow.add_edge("classify",         "generate_content")
workflow.add_edge("generate_content", "build_connection")
workflow.add_edge("build_connection", "generate_quiz")
workflow.add_conditional_edges(
    "generate_quiz",
    lambda s: "enqueue_review" if s["low_confidence_ids"] else "publish",
)
workflow.add_edge("enqueue_review",   "publish")
workflow.add_edge("publish",          END)
```

### 18.3 멀티 에이전트 오케스트레이션 (슈퍼바이저-워커) — 승급 설계

18.2의 단일 에이전트로 도슨트 품질(용어 해설 누락·환각·맥락 부족)이 부족할 때, IBM의 **계층적 분해(hierarchical manager-worker)** 패턴으로 승급한다. **슈퍼바이저**가 "이 이슈로 주린이용 도슨트 생성"을 하위 작업으로 분해해 **워커**에 위임하고, 결과를 종합한다.

```
        ┌──────────── Docent Supervisor (매니저) ────────────┐
        │   작업 분해 · 워커 위임 · 결과 종합 · 게이트         │
        └───┬────────┬────────┬────────┬────────┬────────────┘
            ▼        ▼        ▼        ▼        ▼
        이슈요약  용어해설  종목·기업  배경·맥락  품질검증
         worker   worker  연결(RAG)   worker    worker
                          worker
        └─ 요약·용어·종목·맥락은 병렬 → 품질검증이 종합·게이트 ─┘
```

| 워커 | 단일 책임 | 비고 |
|------|----------|------|
| 이슈요약 | 클러스터 뉴스를 핵심으로 압축 | 멘토 "10줄 이내" |
| 용어해설 | 주린이가 모를 용어를 쉬운 말로 | 장독대 차별점 |
| 종목·기업 연결(RAG) | pgvector에서 관련 공시·재무 검색·연결 | 벡터DB에 없으면 "확실치 않음"(멘토 RAG 엣지케이스) |
| 배경·맥락 | 왜 중요한 이슈인지 풀이 | |
| 품질검증(verifier) | 원문 뉘앙스 보존·환각 검증 → 통과/재생성 | 멘토 LLM 출력 품질 |

- **패턴**: 워커는 **병렬** 실행, 슈퍼바이저는 **계층적 종합**(IBM manager-worker).
- **단일 책임**: 워커 1개 = 작업 1개 (멘토 "한 번 호출엔 하나의 task").
- **승급 기준**: 단일 에이전트 품질이 임계 미달일 때 **약한 부분만** 전용 워커로 분리 → "왜 멀티 에이전트인가"를 품질 데이터로 정당화(포트폴리오 내러티브).
- **주의**: 멀티 에이전트는 토큰·지연·디버깅 비용이 크다(멘토 "과도한 최적화 불필요"). **MVP는 18.2 단일 에이전트로 시작**한다.

## 20. 개발 범위 및 추후 확장

### 초기 범위

- L1 5개, L2 6개 분류 체계 적용
- 충돌 조합 처리 룰을 반영한 LLM 분류 프롬프트
